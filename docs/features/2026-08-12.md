## 递归协议栈（Protocol Stack v1）

 - 原因：前一版把"单层 `classify_ingress` + `plan_for` + 终态 handler"做成了固定分派表，内层再探测（TLS 解密后、CONNECT 隧道 2xx 后）仍散落在各 handler 内硬编码；用户要求的协议状态机是逐层可下钻的栈（SOCKS5 → TLS/SSH/HTTP1/Raw，TLS → HTTP1/HTTP2/Raw，HTTP1 → CONNECT/WebSocket/GitHTTP/RawBody……）。需要把"探测 + 服务 + 可下钻"统一成递归协议栈：serve 对原对端说的协议 = 客户端说的协议，外层代理协议（CONNECT/SOCKS5/absolute-form）端到端保留，MITM 只替换被审计的最内层。

 - 设计：
   - 新增 `crates/hyperhub-core/src/protocol/stack.rs`：`ProtocolHandler { name, detect(&[u8], u16) -> Option<Inspection>, serve(LayerContext) }` 单一 trait 取代 `Detector`/`PayloadHandler` 分离；`LayerContext { inner, client, upstream, peek, depth }`，`peek` 为已消费前缀，服务层用 `PrefixedIo` 回放；`run_stack` 按注册顺序命中层后交给层 serve，`depth >= MAX_PROTOCOL_DEPTH(8)` 或未命中时由 raw 层 `PrefixedIo` 回放后双向桥接，避免无限递归。
   - 注册表 `builtin_protocols()` 顺序 ssh → http_proxy_connect → http → tls → git → raw；`layer_is_audited` 承担原 `plan_for` 的连接级决策门控（命中 MITM 能力层但策略不审计时出栈透传）。加协议 = 新增模块实现 `ProtocolHandler` 并在 `builtin_protocols()` 注册，`handle_authenticated` 尾部分派收敛为 `run_stack(client, upstream, payload, 0, inner)`。
   - 出栈语义：TLS 层 `proxy_https` 解密后由 `serve_decrypted` 下钻 `run_stack`（替换 `serve_https_tunnel` 内硬编码内层分支）；CONNECT 层 `proxy_https_via_http_proxy` 原样转发 CONNECT、中继响应、2xx 后 TLS MITM 再下钻，保留死隧道直连兜底；HTTP 层 `serve_http` 内含 WebSocket 升级、GitHTTP 注入与 RawBody；raw 层 `PrefixedIo` 回放 + 双向透传。
   - 占位层（v1 只识别 + 审计标记，不解析新线协议）：SSH 按 banner 识别后透传并打 ssh 标签（GitSSH/RawChannel 留作后续）；HTTP2 子协议在 `serve_http` 内按 `application/grpc` content-type / Extended CONNECT `:protocol` 打 grpc/websocket/raw 审计标签，不做载荷解析。

 - 验证：`hyperhub-core` 91 个、`hyperhub` 23 个测试全部通过。新增单测覆盖 `run_stack` 深度超限落入 bridge、SSH banner 透传不解析、注册顺序（CONNECT 先于普通 HTTP）、`http2_subprotocol` 标签；新增 e2e 经 `run_stack` 入口验证 TLS→HTTP1、TLS→HTTP2、HTTP1 CONNECT→TLS（CONNECT 原样到达客户端代理、200 中继、ping/pong 贯通）。

## SOCKS5 栈内层（客户端自己的 SOCKS5）

 - 原因："serve 的 SOCKS5 隧道里再套一层客户端自己的 SOCKS5"（app → serve 外层 SOCKS5 → 客户端 SOCKS5 代理 → 目标）在直连入口由 `handle_authenticated` 内联中继解析，但 SOCKS5 不是注册的栈层：套在 TLS/HTTP 隧道内的嵌套 SOCKS5 会落到 raw 透传而不解析内层目标。
 - 设计：
   - 新增 `Socks5Layer` 并注册进 `builtin_protocols()`（顺序 ssh → socks5 → CONNECT → http → tls → git → raw）：`detect` 复用 `is_socks5_greeting`；`serve` 复用 `negotiate_socks5`/`resolve_socks5_target`/`complete_socks5_connect` 将 greeting/CONNECT 原样中继给上游代理，解析内层目标重新过策略（deny 直接回 2 拒绝），成功后读取有界前缀下钻 `run_stack(depth + 1)`；外层 SOCKS5 端到端保留。
   - `client_proxy.rs` 握手函数泛型化为 `AsyncRead + AsyncWrite + Unpin`（原 `&mut TcpStream`），`resolve_socks5_target` 改为接收 `session_id`；`HandlerContext` 增加 `sessions: SessionRegistry` 供栈内层做 Fake-IP 还原；`protocol_for` 上移到 `policy.rs` 供层复用；`PrefixedIo` 增加 `into_inner`。
   - 直连入口（serve 自身 SOCKS5 listener 后的内层 SOCKS5）仍由 `handle_authenticated` 内联处理，保持审计（`client_proxy`/`preserved`）与代理亲和语义；`Socks5Layer` 覆盖深度 ≥ 1 的嵌套场景。
 - 验证：`hyperhub-core` 92 个、`hyperhub` 23 个测试全部通过。新增 `run_stack_relays_nested_socks5_and_drills_down`（greeting 中继 → CONNECT 解析 → 成功应答 → 内层 ping/pong 贯通）与注册顺序断言（greeting 命中 socks5）。

## protocol 目录布局调整

 - 原因：`protocol/handlers/` 原只剩一个放共享上下文的 `mod.rs`，目录名与实际职责不符；各 `*Layer` 全挤在 `stack.rs`，"加协议 = 加模块"不直观。
 - 调整：`handlers/` 恢复为每协议一个文件（`ssh.rs`/`socks5.rs`/`http_connect.rs`/`http.rs`/`https.rs`/`git.rs`/`raw.rs`），`handlers/mod.rs` 只放 `builtin_protocols()` 注册表与共享 `bridge_layer` 透传服务；共享上下文独立为 `protocol/context.rs`（`HandlerContext`/`contextual_error`/`action_name`）；`stack.rs` 只保留栈机制（`run_stack`/`MAX_PROTOCOL_DEPTH`/`LayerContext`/`ProtocolHandler`/决策门控）。
 - 验证：行为不变，`hyperhub-core` 92 个、`hyperhub` 23 个测试全部通过；注册顺序测试随注册表迁至 `handlers/mod.rs`，栈 e2e 测试留在 `stack.rs`。

## HTTP body 捕获（capture_body）

 - 原因：`capture_body` 原本只在透传路径（raw/ssh/git 原生 bridge_layer）落 `.bin`，HTTP 层（`serve_http`，含 TLS MITM 解密后的明文 HTTP）只记 method/path 元数据，不保存请求/响应体；用户要求审计模块支持保存 HTTP body，并明确分层语义：开启 `capture_body` 但 `websocket_capture` 关闭时，不应捕获 ws-over-http 的升级后数据。

 - 设计：
   - 新增流式包裹 `CaptureBody<B>`（实现 `http_body::Body`）：转发数据帧的同时按 `body_limit` 有界捕获（sha256 覆盖全量，落盘截断），body 结束时把记录追加到 `<session>/<conn>-<stream>-up.jsonl`（请求）与 `-down.jsonl`（响应），复用 `CaptureConfig::transcript_paths` 命名与 `prepare_transcript` 权限；每条记录含 `sequence`（请求/响应同号互相关联）、`direction`、`method`、脱敏 `path`、`http_version`、`status`、`content_type`、`size`、`captured_size`、`truncated`、`sha256`、base64 `body`。
   - 结束判定：hyper 在最后一个数据帧后检查 `is_end_stream()` 便不再 poll 到 `None`（Content-Length 场景），因此 `is_end_stream` 与 `poll_frame` 都触发 `finish`，捕获状态用内部可变性保护，`finished` 标志保证只落一次；空 body（`is_end_stream` 即真）走服务侧快速路径直接落一条 size=0 记录。
   - 分层语义：升级请求（HTTP/1.1 Upgrade、h2 extended CONNECT `:protocol`）不归 body 捕获——请求/响应都不包裹；升级后数据由 WS 层按 `websocket_capture` 独立决定，`capture_body` 不兜底。`RequestSender` 泛型化为 `SendRequest<CaptureBody<Incoming>>`（hyper `handshake` 本身对 B 泛型，无需改动握手）；`http_request` 事件 detail 新增 `body_capture` 布尔标记；连接结束时汇总一次 `http_capture` 事件（等待写盘任务完成，附 `transcripts` 与总字节数）。
   - 配置复用：`AuditProfile.capture_body` + `body_limit` + `audit.transcript_dir`（配置校验已要求 capture 开启时必配 transcript_dir），连接级捕获按首个请求的审计 profile 惰性初始化。

 - 验证：`hyperhub-core` 94 个、`hyperhub` 23 个测试全部通过。新增 `enables_http_body_capture_only_when_profile_captures_bodies`（仅 capture_body profile 生效）与 e2e `captures_http_bodies_but_skips_websocket_upgrades_when_ws_capture_is_off`（POST 截断到 4 字节 + 空 body GET 记录 + websocket_capture=Off 时升级不产生任何捕获文件、两侧各只有两条记录且无 WS 帧）。

## 协议感知的路由匹配（rule.protocol 纳入 matches_connection）

 - 原因：同目标、同优先级的多条 route 原先在连接级 `matches_connection` 不比较 `rule.protocol`，命中顺序只取决于配置插入顺序；用户配置"同目标一个 http 规则、一个 git 规则"时，git 流量可能落到 http 规则上，行为不可预期。

 - 设计：`CompiledRule::matches_protocol` 在连接级把探测到的协议纳入匹配——`Unknown`（尚未探测）保持宽松（仍由优先级→插入顺序决定），已知协议按 `rule.protocol` 精确命中：`Http` 探测命中 Http/Auto/Tcp 规则，`Tls` 命中 Http/Https/Auto/Tcp（web 家族，git 规则不抢占 HTTPS），`Git` 命中 Git/Auto/Tcp，`Ssh` 命中 Ssh/Auto/Tcp。`refine_route_from_inspection` 二次决策因此对已知协议确定唯一；`Auto`/`Tcp` 仍是任意协议兜底。

 - 验证：`hyperhub-core` 95 个、`hyperhub` 23 个测试全部通过。新增 `same_target_same_priority_routes_hit_precisely_by_observed_protocol`：同优先级 http+git 规则在 Git/Tls/Http/Ssh 探测下分别精确命中，顺序反转不影响，Tcp 兜底仍可命中。

## 路由目标模型：删除 target_regex，targets 支持 URL 形式

 - 原因：`target_regex` 是面向导入配置保留的旧正则匹配器，与友好 `targets` 双轨并存造成"同目标同优先级命中谁"的额外歧义；用户要求彻底删除，并把 URL 形式纳入 targets，使"按目标 URL（含路径）精确命中"成为一等能力。

 - 设计：
   - `RouteRule.target_regex` 彻底移除；`RouteRule` 新增 `#[serde(flatten)] legacy` 占位捕获旧键，`Config::validate` 对仍含 `target_regex` 的配置报错（提示改用 targets/http_path_regex），避免删除正则约束后规则静默放大匹配范围。
   - `targets` 条目新增 URL 形式 `[http(s)://]host[/path]`（host 支持 `*.` 前缀；不支持端口，端口请用 ports 字段；路径不得含查询/片段）。解析统一走 `parse_route_target -> RouteTarget { Domain{host,path_prefix}, Ip, Network }`，config 校验、TUI 归一化与策略编译共用同一实现。
   - 匹配语义：连接级仍按主机（域名/IP/CIDR）匹配，URL 路径不参与；HTTP 家族按请求匹配（`matches_http`）时，URL 条目命中主机后要求路径命中其前缀（`/api` 命中 `/api`、`/api/...`，不命中 `/api2`；无前缀条目放行该主机所有路径）；非 HTTP 协议无路径概念，URL 目标退化为纯主机匹配——满足"URL 只在 http 及基于 http 的协议生效"。
   - `PolicySnapshot::compile` 错误类型改为 `String`；`decide_http` 的 `http_target_matches` 与 `http_path_regex` 为 AND 关系。

 - 验证：`hyperhub-core` 98 个、`hyperhub` 23 个测试全部通过。新增 `parses_url_form_targets_with_http_only_schemes`（URL 解析与非法形式）、`rejects_removed_target_regex_field_on_validation`（旧配置迁移报错）、`url_form_targets_match_request_paths_only_for_http_family`（/v1 前缀命中、/v2 与大小写不命中、无前缀主机放行、SSH 规则 URL 目标退化为主机匹配）；原 `target_regex` 用例迁移为等价 `targets` 断言。

## git 与普通 Web 同目标按请求注入不同凭证

 - 原因：`https://test.com` 场景下，TLS 解密后请求级 `derive_request_context` 只复制连接级协议（`Tls`），git-over-https 与普通 Web 请求在 `decide_http` 中无法区分；Git 规则按请求命中需要 `context.protocol == Git`，因此两个请求都会落到 Http 规则、注入同一凭证。

 - 设计：`serve_http` 按请求做协议精化——`inspect_git_http(method, path)` 命中（`/info/refs?service=git-upload-pack`、`/git-upload-pack` 等）时把 `request_context.protocol` 置为 `Protocol::Git`，再执行 `decide_http`。由此：git 请求命中 Git 规则（注入 git 凭证），普通请求保持 Http/Tls 命中 Web 规则（注入 web 凭证）；明文 git-over-http 连接级已探测为 Git，行为不变。连接级仍按原语义（TLS 归 web 家族，Git 规则不抢占 HTTPS 连接决策，MITM 由 Http/Https 规则或兜底驱动）。

 - 验证：`hyperhub-core` 99 个、`hyperhub` 23 个测试全部通过。新增 e2e `mitms_tls_and_injects_git_credential_only_for_git_requests`：TLS(ALPN http/1.1) + 同目标 Http/Git 双规则 + Bearer 凭证，origin 断言 git 请求带 `Authorization: Bearer git-token`、普通请求带 `Bearer web-token`；`read_headers` 测试助手泛型化为任意 `AsyncRead`。

## 协议栈逐层以最后发现的协议精化路由匹配

 - 原因：协议栈逐层下钻（CONNECT/SOCKS5 → TLS → HTTP/git/SSH/raw）时，连接级决策只在入口做一次；最内层探测（如 TLS 解密后的 git smart-http、嵌套 SOCKS5 内的 TLS/SSH）无法驱动 gate/审计/deny。用户要求"以最后发现的协议作为目标协议，基于它重新匹配 route"。

 - 设计：
   - `run_stack` 命中非隧道层（tls/http/ssh/git）后，先以该层 `detect` 的 `Inspection` 调用共享 `refine_route_from_inspection`（从 `socks.rs` 上移到 `protocol/stack.rs`，经 `protocol::` 再导出，`socks.rs` 入口与栈内共用同一原语），gate/审计/deny 全部使用精化后的决策；隧道层（http_proxy_connect/socks5）不精化——CONNECT/SOCKS5 目标可承载任意协议，其决策已在 `socks.rs` 入口或 `socks5.rs` 内按解析出的目标完成。
   - 精化后若决策为 Deny：审计 `authorize/deny/denied` 并直接返回，不再进入层服务（git/ssh deny 规则在 TLS 解密后才命中时，连接在 serve 前被拒绝，不转发任何字节）。
   - 兼容性：`CompiledRule::decision` 已有"Http 规则在 Tls 观测下转 Https"的规则，TLS 层精化不会误关 MITM 门控；无规则命中时按探测推断兜底协议（`inferred_route_protocol`），HTTP 层因此从"仅 Http/Git 决策走 serve_http"自然扩展为"解密后的明文 HTTP 均走 serve_http"。

 - 验证：`hyperhub-core` 102 个、`hyperhub` 23 个测试全部通过。新增 `run_stack_refines_to_innermost_git_rule_and_injects_credential` 与 `run_stack_refines_to_innermost_web_rule_and_injects_credential`（TLS 入口决策 + 同目标 Http/Git 双规则：最内层探测驱动 serve_http 并分别注入 git/web 凭证），以及 `run_stack_denies_when_innermost_protocol_matches_deny_rule`（git deny 规则在 TLS 决策态不命中、最内层命中后拒绝且不向任何一侧转发）。

## 层能力枚举与纯函数精化（收敛重构）

 - 原因：上一版逐层精化在 `run_stack` 与 `layer_is_audited` 中用层名字符串（"tls"/"http"/"http_proxy_connect"…）判断是否参与精化/门控，加协议时要同步维护多处字符串列表，与"加协议=加模块"冲突；`refine_route_from_inspection` 以写后覆盖方式修改 `context.protocol`，可读性差。

 - 设计：
   - `ProtocolHandler` 新增 `fn kind(&self) -> LayerKind`；`LayerKind` 为行为能力枚举：`Tunnel`（HTTP CONNECT：不精化，按 HTTPS 家族门控）、`Passthrough`（SOCKS5/raw：不精化、不门控，socks5 在层内解析目标后自决策）、`Https`（TLS：精化 + HTTPS 家族门控）、`Http`（明文 HTTP：精化 + HTTP 家族门控）、`Native`（SSH/Git 原生：精化但不参与 MITM 门控）。`run_stack` 与审计门控只按枚举分派，不再出现层名字符串；加协议 = 新模块实现 `kind()` 声明自身行为。
   - `refine_route_from_inspection(policy, context, inspection) -> RouteDecision` 纯函数化：克隆上下文置探测协议后重新 `decide`，由调用点统一 `decision = refined; context.protocol = protocol_for(decision.protocol)`，消除写后覆盖；`socks.rs` 入口与栈内共用。

 - 验证：`hyperhub-core` 103 个、`hyperhub` 24 个测试全部通过；新增 `layer_kind_declares_refinement_and_gate_capabilities`（各变体精化/门控能力断言），既有三个 gate 测试改为按 `LayerKind` 断言，行为不变。
