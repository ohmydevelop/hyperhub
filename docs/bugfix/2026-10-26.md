## 动态附加的内存与进程回归（开发中，未发布）

本记录只描述 `dev/dynamic-attach` 的不可变开发候选和本地源码回归，不代表稳定版影响范围或发布验收已经完成。

- Gum fork 恢复曾在返回门与监听器退休之间互等：管理器卸载临时 Frida 脚本时等待仍在执行的旧回调，子进程又在该回调中等待管理器放行。两侧原生栈确认该循环；child 恢复保留继承监听器后，r13 完整 tree 两轮的 fork/exec/vfork、环境和再次附加检查通过。并发 Preparing 与退出清理仍需单独验收。
- 初次注入的初始化线程曾在分配器持锁时进入 `mprotect` Hook，而 Hook 读取映射时再次分配内存。实际启动栈和旧候选的通用冷线程分配样例均触发失败。源码改为初始化线程的内部作用域及匿名映射的无分配通路，首次注入和普通 tree 回归已通过；更严格的线程创建、并发映射与 FD 故障回归尚未全部通过，不能把它们记为完成。
- 旧候选 r10 对文件映射的访问控制存在两个已实测的读取绕过：路径包含空格时，按空白拆分映射记录丢失真实路径；FD 耗尽时，读取映射失败被当成没有文件映射。私有诊断对照保留原有策略断言，仅跳过会先卡住的 Active 分配器阶段，分别读到了可丢弃的受保护样例字节。r13 普通路径已同时拒绝映射读取和 FD 压力下读取，其他路径的完整回归仍被线程创建失败阻断。
- 原 root 自我 exec 后曾丢失 Hook，同时记录仍为 Active。r13 同 PID 的首次读取继续被拒绝，记录的可信执行代次由 0 推进到 1，原始审批身份保留。连续同映像、不同映像、非主线程、基于 FD 的 exec 和旧审批交错仍需后续真实验收。
- Core 发布历史时持锁等待 Host 反向确认，而 Host 激活又同步请求注册，存在锁顺序循环。源码分离操作串行锁与短时历史状态锁，反向 IPC 在状态锁外完成；真实私有 Host 的确定性交错测试已通过。根映像及成员变动的端到端覆盖仍须继续。

Linux 源码入口与统一 Suite 位于 [动态附加驱动](../../scripts/test-dynamic-attach.py)、[目标样例](../../tests/fixtures/dynamic_attach_target.c) 和 [Linux Suite](../../scripts/benchmark-linux-backends.sh)。终端回归还检查完整可见输出、键盘字节、应用退出后的模式恢复；Windows 同类匿名 section 样例只完成 GNU 交叉编译，尚未原生执行。精确候选摘要、失败现场和未完成项保留在根目录 `PLAN.md`。

普通线程创建的独立回归进一步确认：r13 的 `pthread_create` 返回 `EACCES`，已成功启动的线程仍能完成分配与内容校验。仅捕获错误分支的原生调试显示，普通 `mprotect(..., 65536, PROT_READ|PROT_WRITE)` 被映射解析器以地址区间格式错误拒绝；不是内核权限错误。独立源码 oracle 在并发 VMA 变化下复现了共享 proc 描述符上独立 `pread` 字节偏移导致的记录错位，而串行顺序游标保持零解析错误。

当前源码改为无堆分配、无 SDK TLS 的原始 futex 游标锁及 `lseek`/`read` 顺序遍历；文件区间的临时标量记录通过原始内存映射保存，在原始业务 `mprotect` 前释放，策略与路径处理均在游标锁外执行。错误策略保持原值。新增独立线程模式和游标 oracle 已注册统一 Suite；r13 上的新线程模式实际在首轮 Active 返回错误，源码修复后的嵌入候选和完整自动测试仍待主 agent 构建执行，不能记为验收通过。

R14 的分配与普通线程回归通过后，独立“冷线程分配→fork→子进程 libc `_exit(0)`→父进程 waitpid”源码仍实际停止。子进程的原始管道标记证明 fork 已返回应用代码；调试栈停在 Frida Core ExitMonitor 的条件变量等待，父进程停在 wait4。子进程 SDK 已处于未托管状态；关闭管理器诊断采样的三次控制也失败，故不能把采样帧当作原因。Frida 17.17 的 [ExitMonitor 源码](https://github.com/frida/frida-core/blob/17.17.0/lib/payload/exit-monitor.vala) 说明，该可选回调会等待异步退出准备。

内部 Core 会话现在通过官方 SessionOptions 关闭该退出监视器。Core 的 fork/exec 监控、HyperHub 的策略 Hook 和基于 OS/启动器的退出观察均保留。中性回归同时覆盖原生、策略生效、解除后阶段，并在多个 fork 批次前重新创建冷线程；管道标记不代表退出完成，最终仍要求真实回收成功，原有总等待时限保持 30 秒。原生 32 次 fork/8 个冷线程批次实际通过、root 退出码为 37；修复后的嵌入候选仍待主 agent 构建和执行，不能将源码改动记为最终验收通过。

R15 已在实际隔离 Linux 环境验证：process 作用域的中性退出回归全部通过；普通、空格、换行及字面 `(deleted)` 四种映射路径各完成两轮附加／解除回归。tree 作用域的 Active 子进程退出已完成，但管理器报告 fork 发布确认超时，解除审批失败，因此 tree 全流程仍未通过。新发现短命子进程可能在发布线程写入确认前退出，正在修复确认与放行顺序；并未增加超时或把失败改为成功。R15 同源码默认工作区测试 716 项通过、25 项忽略，Gum SDK 75 项通过；仍不能替代完整生命周期与目标平台验收。

Linux 统一 Suite 原先在受限 Yama 上仍会启动显式 Gum 正例；仅拒绝测试模式又可能被报告为完整 PASS。入口和嵌套语义回归现使用同一只读能力分类，保留 ptrace/native 与可执行的权限拒绝场景，为未执行的 Gum 正例记录原因。报告区分失败、完整通过和部分覆盖；空检查、未知状态及重复检查 ID 不得通过。新增 11 项临时文件/命令桩测试已通过，无需修改系统策略；完整原生 Suite 与更新后的嵌入候选仍待主 agent 执行。
