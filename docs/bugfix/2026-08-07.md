# Bugfix 记录

## 2026-08-07：服务启动时报“系统找不到指定的路径”

- 现象：使用示例配置启动 `hyperhub serve` 时返回 `os error 3`。
- 原因：审计日志配置为 `audit/hyperhub.jsonl`，但日志文件的父目录不存在，服务直接打开文件失败。
- 修复：`AuditWriter::open` 在打开日志前自动创建非空父目录。
- 验证：新增 `creates_audit_parent_directory` 测试；示例配置可直接启动并自动生成审计目录和日志文件。

## 2026-08-07：注入 curl 后域名解析失败

- 现象：Agent 已成功注入并 Hook `getaddrinfo`，但 curl 返回 `Could not resolve host`。
- 原因：控制面 `ResolvedName` 响应包含 `ttl_secs`，Agent 的严格反序列化结构未声明该字段，导致合法 DNS 响应被拒绝。
- 修复：Agent 接收并兼容 `ttl_secs` 字段，DNS Hook 正常返回服务端解析结果。
- 验证：新增 `accepts_resolved_name_control_response` 测试；通过注入后的 curl 请求 `https://baidu.com` 成功收到 HTTP 301，审计日志记录对应连接。

## 2026-08-07：百度 HTTPS 示例缺少 CA 时只显示 os error 3

- 现象：直接使用 `examples/baidu-curl.toml` 启动 `serve` 时，仅显示“系统找不到指定的路径 (os error 3)”，无法判断缺失内容。
- 原因：示例引用的本地 CA 尚未生成；配置校验只检查 CA 字段是否成对出现，TLS 初始化又直接透传文件系统错误，丢失了字段和文件路径上下文。
- 修复：配置校验增加 TLS/SSH CA 文件存在性检查；TLS 初始化错误补充证书或私钥的完整路径及解析阶段；为本地百度测试生成 CA。
- 验证：新增 `rejects_missing_ca_files_with_the_field_and_path` 测试，并使用百度示例配置启动 `serve`。
- 后续：动态根 CA 架构已删除 TOML `trust` 和磁盘 CA 前置条件，因此该错误路径及对应校验不再存在。

## 2026-08-07：Schannel curl 仍拒绝进程内 HyperHub 根 CA

- 现象：Agent 已把动态根 CA 加入 `CertGetCertificateChain` 的附加内存 Store，但 curl 仍返回 `SEC_E_UNTRUSTED_ROOT`。
- 原因：该 Schannel curl 通过 SSPI 函数表创建版本 5 凭证，并启用了自动凭证校验；`hRootStore` 只用于服务端客户端证书认证，不能给客户端服务器证书校验增加根。最初同时保留 `SCH_CRED_AUTO_CRED_VALIDATION` 与手工校验标志也导致自动校验继续先行失败。
- 修复：Agent Hook SSPI 函数表，清除自动校验标志并启用手工凭证校验；握手完成后取得远端证书，使用“系统 ROOT + 当前 HyperHub ROOT”构建证书链并执行服务器名称、用途、有效期和签名策略校验。只有精确终止于当前 HyperHub 根 CA 的链会忽略 `CERT_TRUST_IS_UNTRUSTED_ROOT`，其他错误保持失败。根私钥不下发，系统证书库不修改。
- 验证：使用 PortableGit Schannel curl，不传 `--cacert` 请求 `https://baidu.com`，并检查 HTTP 与注入审计结果。

## 2026-08-07：百度测试 Header 规则会命中所有 curl HTTPS 请求

- 现象：百度测试配置只限制 `curl.exe` 和端口 443，其他 HTTPS 域名也会被注入 `TEST` Header。
- 原因：路由缺少 `target_regex`，进程和端口条件不足以限定目标站点。
- 修复：合并后的统一配置增加 `target_regex = "(?i)(^|\\.)baidu\\.com$"`，只匹配 `baidu.com` 及其子域名。
- 验证：统一配置通过校验；`www.baidu.com` 命中 `baidu-curl-https`，非百度域名不满足该路由的域名条件。
# Git HTTPS 子进程未被注入（待修复）

- 现象：`hyperhub git ls-remote https://github.com/...` 可以访问 GitHub，但审计日志没有连接记录，GitHub Route 也没有命中。
- 原因：`git.exe` 将 HTTPS 网络请求交给 `git-remote-https.exe` 子进程；当前 Windows 启动器只注入根进程，没有向新建子进程传播 Agent。
- 当前验证方式：将 `git-remote-https.exe` 纳入 GitHub Route，并直接作为 HyperHub 目标执行端到端测试。
- 后续修复：Hook `CreateProcessW/CreateProcessA`，以挂起状态创建子进程并注入同一 Agent，同时让控制面把子 PID 关联到根会话。修复前不能把 `hyperhub git ...` 的成功当作已审计。
# GitHub Git HTTPS 使用 Bearer 导致认证失败

- 现象：GitHub REST `/user` 认证成功，但 `git ls-remote https://github.com/...` 返回 `invalid credentials`。
- 原因：原配置对全部 GitHub HTTPS 流量注入 `Authorization: Bearer`；Git Smart HTTP 的 PAT 认证使用 HTTP Basic。
- 修复：拆分 GitHub API 与 Git Smart HTTP 凭证；`api.github.com` 使用高优先级 Bearer Route，普通 `github.com` Git 流量使用 `x-access-token:PAT` 的 Basic Route。
- 验证：GitHub API 返回成功；Git Smart HTTP 命中 `github-https`，审计只记录 `authorization` Header 名称，不记录值。
# QBDI 指令回调覆盖异步 Winsock LastError

- 现象：`ConnectEx` 已正确重定向，但无调试环境变量时 Go 客户端报告“系统找不到指定的环境选项”；开启 Agent 调试后反而成功。
- 原因：`ConnectEx` 以 `FALSE + WSA_IO_PENDING` 表示正常异步提交，指令回调随后调用 `GetEnvironmentVariableA` 检查调试开关，将线程 LastError 从 `WSA_IO_PENDING` 覆盖为 `ERROR_ENVVAR_NOT_FOUND (203)`。
- 修复：API 适配函数返回后立即保存 LastError，完成调试与寄存器处理后再恢复，保持 Windows/Winsock 调用约定。
- 验证：不设置 `HYPERHUB_AGENT_DEBUG` 时重复执行 `gh api user --silent`，无效占位 Token 被 HyperHub 替换且请求成功。
# Go 线程使用独立 QBDI 虚拟栈导致退出长尾

- 现象：`gh api` 单次认证成功，但连续运行时目标可能在请求结束后长期不退出。
- 原因：新线程 trampoline 使用 `switchStackAndCall` 创建独立虚拟栈；Go runtime 从 Windows TEB 获取 OS 线程栈边界，虚拟栈地址不在该范围内，破坏线程调度和退出假设。
- 修复：在线程原生栈内预留对齐执行区域，直接初始化 QBDI 的 `RCX/RSP/RIP` 并运行原始线程入口，保持目标栈位于 TEB 描述的范围内。
- 验证：连续运行 `gh api user --silent`，检查请求成功、进程正常退出及每次授权审计。
# 动态证书缺少 AKI 被 OpenSSL 严格模式拒绝

- 现象：Python/OpenSSL 的 TCP 已通过 HyperHub，但 TLS 验证报告 `Missing Authority Key Identifier`；Schannel/curl 不报错。
- 原因：动态 CA 和叶子证书使用 rcgen 默认参数生成，默认不写 Authority Key Identifier；新版 OpenSSL 的严格链验证拒绝该证书。
- 修复：CA 和每张动态叶子证书都启用 `use_authority_key_identifier_extension`，使签发链包含 RFC 5280 所需的密钥标识关联。
- 验证：Python `urllib.request` 不指定 CA 文件即可通过 Agent 获取信任材料并完成 GitHub HTTPS 请求。
# 手工模拟 API 返回破坏 CFG/CET 返回语义

- 现象：指令 Hook 可运行 `gh.exe`，但系统 CFG curl 以 `0xC0000409` 快速失败。
- 原因：早期回调直接弹出目标栈返回地址并修改 `RSP/RIP/RAX`，没有经过真实 `ret`，与 CFG/CET 保护的调用返回状态不一致。
- 修复：API 入口回调只将 `RIP` 重定向到同签名适配函数，保留调用方原始栈；适配函数完成后用真实 `ret` 返回，参数、异常展开、LastError 和控制流保护均由原生 ABI 维护。
- 验证：Go `gh.exe`、PortableGit curl、Python/OpenSSL 分别完成 HTTPS 请求并命中审计；XFG 目标启动前明确拒绝，不再进入崩溃路径。

# Python 默认 OpenSSL 上下文未加载 Agent CA

- 现象：Python 的 TCP 已被重定向，显式指定 `SSL_CERT_FILE` 可返回 200，但默认 `urllib.request` 报自签名证书错误。
- 原因：Python 3.13 在 Windows 上优先加载系统证书库，目标运行时没有自动把环境变量中的 Agent CA 合并进 OpenSSL `SSL_CTX`；`libssl` 又是 `_ssl.pyd` 的递归依赖，单看 `LoadLibrary` 返回模块无法发现。
- 修复：每次 `LoadLibrary*` 完成后重新枚举非系统依赖模块；发现 OpenSSL 后拦截 `SSL_CTX_set_default_verify_paths` 和 `SSL_CTX_load_verify_locations`，保留原信任并追加 HyperHub 根。
- 验证：Python 默认 `urllib.request.urlopen` 无需 CA 参数即可返回 200，默认 CA 数量从 48 增至 49。
