## Gum Agent 保留进程内 loopback IPC

> 此临时绕过方案已被下方“Loopback 代理流量绕过审计”修复取代。

- 原因：Gum Agent 最初把目标进程的所有 loopback `connect` 也重定向到 `serve`。PortableGit curl 的异步 DNS resolver 使用本地 socketpair 唤醒工作线程，内部连接被改写后表现为 `getaddrinfo() thread failed to start`。
- 影响：使用内部 TCP loopback 做线程唤醒或进程内 IPC 的目标可能在真正发起外部连接前失败。
- 修复：Gum Hook 默认保留 IPv4/IPv6 loopback 连接，只接管非 loopback TCP；确需审计 loopback 时可设置 `HYPERHUB_INTERCEPT_LOOPBACK=1`。
- 验证：PortableGit curl 8.19.0 的异步 DNS 恢复正常，经 Gum Agent 请求百度返回 200 并连接 Fake-IP；系统 curl 与静态 Go `gh` 同时保持正常。

## Loopback 代理流量绕过审计

- 原因：Agent 默认跳过所有 IPv4/IPv6 loopback `connect`，导致目标使用 Windows 系统代理或本地 Clash 等 HTTP/SOCKS5 代理时直接连接代理端口，无法进入 HyperHub 数据面。
- 影响：同一目标的直连 WebSocket 会被审计，而 fallback HTTPS 可能绕过 `serve`；路由、凭证注入和审计行为取决于目标是否使用本地代理，不再无感一致。
- 修复：移除 loopback 分类与 `HYPERHUB_INTERCEPT_LOOPBACK` 开关，所有 TCP 目标统一重定向。仅由 Rust agent-core 精确排除 HyperHub 自身 SOCKS 入口，并保留线程递归保护；原始 HTTP/SOCKS5 代理继续由 `serve` 识别和保留。
- 验证：增加 loopback 原始代理端点必须被接管、HyperHub 自身入口必须绕过的单元测试，并重新运行 workspace 测试。使用注入后的系统 curl 显式连接 `127.0.0.1:7897` 请求 `https://chatgpt.com/` 返回 HTTP 403，审计记录 `client_proxy_protocol=http`、原始代理端点及最终 OpenAI route，证明流量经过 HyperHub 后仍由原代理送出。

## Serve 继承标准代理环境变量

- 原因：未配置 TOML upstream 时，`serve` 直接调用 `TcpStream::connect`；该 API 不会自动使用 `HTTPS_PROXY`、`HTTP_PROXY` 或 `ALL_PROXY`，导致必须经本机代理访问的 HTTPS/WebSocket 目标直接连接超时。
- 影响：被 Hook 程序即使运行在已设置代理变量的环境中，HyperHub 建立的下一跳仍可能绕过代理；审计失败分支还会把默认 `passthrough` 错记为 `proxy`。
- 修复：`serve` 启动时读取大小写代理变量，按 HTTPS、HTTP、其他 TCP 选择代理，支持 HTTP CONNECT、SOCKS5、URL Basic 凭证和 `NO_PROXY`；显式 route upstream 保持最高优先级，并绕过代理自身端点以防递归。审计改为记录真实 route action。
- 验证：增加代理优先级、认证脱敏、域名/端口/IP/CIDR 绕过、自循环保护及真实 HTTP CONNECT 握手测试。

## TLS UnknownCA 无法定位方向

- 原因：TLS MITM 的客户端接受握手与真实上游连接都直接向上传递 TLS 库错误，顶层 `socks_connection_error` 又没有 session、connection 或处理阶段。
- 影响：`received fatal alert: UnknownCA` 无法直接判断是目标拒绝 HyperHub 动态证书，还是 HyperHub 拒绝真实目标证书，也无法稳定关联到并发连接。
- 修复：分别标记 `client TLS MITM handshake` 与 `upstream TLS handshake`，并在顶层错误中加入 session ID、connection ID、PID 和 phase；`--debug` 可实时查看相邻生命周期事件。
- 验证：TLS 与连接测试保持通过，实际状态接口能按连接键返回 `tls_mitm` 阶段。

## WebSocket Upgrade 双向转发

- 原因：HTTP 处理器只把握手当作普通 request/response 转发；收到 HTTP/1.1 `101 Switching Protocols` 或 HTTP/2 Extended CONNECT `200` 后，没有取得客户端与上游的 upgraded stream，WebSocket 帧因此无法继续传输。
- 影响：Codex 的 WebSocket transport 会断开并降级为 HTTPS；其他依赖 HTTP Upgrade 或 RFC 8441 的长连接同样不可用。
- 修复：HTTP/1 上下游连接启用 Hyper Upgrade，HTTP/1 客户端固定使用 HTTP/1 ALPN；HTTP/2 服务启用 Extended CONNECT。请求完成路由、Header 注入和审计后，`serve` 同时接管两侧 upgraded stream 并执行全双工转发，关闭时记录字节数、耗时和结果。
- 验证：新增 HTTP/1 Upgrade 与 HTTP/2 Extended CONNECT 端到端测试，均验证握手后的客户端→服务端和服务端→客户端字节传输。

## 未知协议被标准端口处理器误接管

- 原因：无 route 时先按 80/443 等标准端口选择 HTTP/HTTPS 处理器；TCP relay 与 HTTP Upgrade 又使用不同复制循环。443 上的未知明文、非 HTTP TLS 或自定义 ALPN 可能在连接可透传的情况下被 HTTP 解析失败中断。
- 影响：未知 TCP 协议需要额外声明 `protocol = "tcp"` 才能可靠工作，也无法保证 TLS 解密探测后的首包被完整交还给透传层。
- 修复：新增共享 `DuplexBridge`，统一普通 TCP、转录、TLS raw stream 与 HTTP Upgrade 的双向转发和字节统计；使用 `PrefixedIo` 回放探测数据。无明确 route 时按首包修正端口推断，自定义非 HTTP ALPN 直接使用原始 TCP；TLS 解密后不是 HTTP 时关联现有两侧 TLS 流继续透传。
- 验证：增加未知双向字节、分片 HTTP 探测、未知 TLS 首包保留、TLS SNI/ALPN 解析及自定义 ALPN 回退测试，原有 HTTP/1、HTTP/2、SOCKS5 与转录测试保持通过。

## 同一目标的独立连接丢失客户端代理亲和性

- 原因：`serve` 只能在单条连接收到 HTTP CONNECT 或 SOCKS5 握手后识别目标原有代理；同一会话随后对同域名建立的独立 TCP 连接没有该上下文，会在未配置环境代理时错误直连。
- 影响：普通 HTTPS 可经目标原有代理访问，但 WebSocket 或其他独立传输可能直连超时；是否能联网取决于目标内部各网络栈的代理选择。
- 修复：按 session、目标域名和端口缓存已观察到的客户端 HTTP/SOCKS5 代理。显式 route upstream 和环境代理保持更高优先级，其余同目标连接自动复用该下一跳；实现不包含进程名或应用专属规则。
- 验证：增加代理亲和性作用域单元测试，确认只匹配同 session、同域名、同端口，并保持 workspace 测试全绿。
