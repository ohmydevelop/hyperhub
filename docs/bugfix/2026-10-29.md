# 2026-10-29 Bugfixes

## Dynamic attach cleanup remains authoritative after a preparation failure

- Publish a consumed Detach authorization to the resident manager before any fallible Core fence. A failed fence now remains an approved cleanup operation instead of losing a one-use authorization or inviting an impossible replay.
- Refresh the authorization once per cleanup round. Gum and ptrace managers independently re-establish the Core detach fence before changing Host policy or physically detaching.
- Bound Frida cleanup settlement to one owner and one stable cleanup flight. A fork-listener setup that failed before publishing a permanent owner may use the unowned native abort transaction only when the same Frida context confirmed that the temporary script unloaded successfully.
- Keep the resident manager alive after a failed initial preparation reaches `DetachedResident`. The original preparation error remains diagnostic context and no longer overwrites the successfully cleaned state as lost management.
- Treat an already published `CleanupPending` record as transitional only after the live manager synchronously accepts the Detach approval. Other cleanup-pending observations remain immediate test failures.

Regression coverage includes the Rust authorization and fence ordering tests, the deterministic JavaScript rearm/abort oracle, driver wait-state tests, the full workspace and embedded release build, and isolated Linux KVM runs for three single-worker busy preparations, one two-worker run, and manager exit during approval review.
