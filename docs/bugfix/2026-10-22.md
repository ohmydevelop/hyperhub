## fork、线程析构与原生模块生命周期

真实 Gum 子树回归定位到另一处加载器锁等待：短命 exec 子进程退出期间，Frida 新线程经分配器进入匿名 mmap Hook，Engine 调用上下文首次初始化会注册 Rust 线程析构器并等待加载器锁。原生符号栈保留在 `target/diagnostics/native-gum-orphan-exec-symbol-stack.log`。

调用上下文改用预先创建的 pthread key / Windows FLS 槽，线程或 Fiber 退出时释放实际 Slot 与 Lease；晚到析构中的业务 Hook 使用立即回收的临时槽，继续执行策略。Windows 每次读取实际当前 Fiber 的 FLS 槽，删除另一 Fiber 时只清匹配槽，避免跨 Fiber 的线程缓存悬空；语义依据 [Microsoft FLS 契约](https://learn.microsoft.com/en-us/windows/win32/api/fibersapi/nf-fibersapi-flsgetvalue)。匿名 mmap 不进行无关的文件策略调用。

fork 重建不解锁或析构父线程继承的 MutexGuard；子进程重建锁、原生 owner 和存活引用，丢弃消失线程的引用。相同 DSO 的多 owner 计数决定真实缓存析构，最后 owner 释放后才回收，不能在普通卸载中永久泄漏缓存。

父进程退出还会使 Gum 子进程失去 Yama 要求的祖先关系。CLI 在管理期间作为子树 subreaper，保持对孤儿后代的祖先关系并回收其实际退出状态；退出后恢复此前设置。未修改系统 ptrace 配置，也未向任意进程开放调试权限。依据 [Linux subreaper 契约](https://man7.org/linux/man-pages/man2/pr_set_child_subreaper.2const.html)。真实 ptrace/Gum 普通及 root 先退出的子树场景已通过本机回归；Windows 原生线程/Fiber 行为仍由最终 CI 验证。

## 发布恢复与不可逆决定

- helper 收到直接成功确认后，事务可能先进入排空阶段；进程回收现在独立于安装阶段及日志错误，避免遗留僵尸进程。
- 被中断的文件复制可能留下半写暂存文件。暂存名加入持久化安装尝试编号，后续恢复使用新文件，保留旧冲突文件；同一次尝试的完整暂存及备份仍可按摘要恢复。Unix 恢复时也校正执行权限。
- Engine 已持久化 finalize 而发布日志尚未更新时，不能再受理 Abort。发布协调器同 tick 记录不可逆决定，并在受理 Abort 时复查 Engine 的持久状态；Engine 日志冻结时先要求恢复。发布 Recover 同时恢复已有 Engine 事务。
- 全局升级比较常驻版本、当前 worker 和已完成发布/Engine 的版本下界，不能在没有 Host 或内建版本较旧时降级稳定部署。局部高级 Engine 实验保留单独语义。

这些边界使用状态机、真实短进程 helper、持久回执和私有 Home 的原生发布回归验证；不以正常升级成功代替故障恢复断言。最终发布和平台验证以精确提交 CI 为准。

## 长策略标识的返回容量

文件、进程和防火墙决策会在返回值中重复规则标识及 Protection。合法的长 ASCII 或 Unicode 标识可能使返回 JSON 超过原有 4 KiB 缓冲区，导致调用方错误进入策略异常分支。正常调用仍使用 4 KiB；只有这三种无副作用的字节决策在明确收到容量错误时，才使用同一个 Lease 有界重试一次。输入上限继续生效，其他操作和业务 IO 不重试。

内建与真实 DSO 回归覆盖长标识、Protection 放大及最终决策字段；计数回归确认只重试一次、其他操作不重试、超限输入不调用 Engine。静态调用包装属于原生基座，已纳入兼容指纹，必须随新 Agent/CLI 构建，不能宣称仅热换 Engine 就修复旧基座。

## forwarding 控制通道断开后的会话取消

源程序模拟上游在收到 EOF 后仍不返回，并让 worker 控制通道先断开。原实现保留的父进程连接 Lease 无法识别单会话撤销，直到整个 worker 退出才释放。真实反例记录在 `target/diagnostics/forward-worker-cancel-halfclose-before.log`。

现在 resident 与 worker 在 accepted TCP socket 上共享显式关闭标记，在完成或取消时先设置标记再关闭两向；正常远端 FIN、半关闭和排队的上传字节不被解释成撤销。该标记不消费或写入应用数据。故障回归同时保留另一个会话的长连接，要求被取消会话及时释放 Lease 和阻塞上游，而另一个会话继续 echo；并覆盖正常半关闭下载、上传和控制通道丢失后的完成清理。统一 Linux/Windows worker Suite 均注册这些源码测试，Windows 实际结果以最终原生 CI 为准。

补充复审修复两处失败清理：已获 Grant 的连接若因文件描述符耗尽而无法复制取消探针，现在使用原始共享 socket 发布完成标记，避免控制通道也已断开时父进程一直等待已无法转发的连接；控制通道断开后，尚未获得 Grant 的记录立即释放，已获 Grant 的连接仍保留取消监听。独立 Unix 测试子进程通过真实 `RLIMIT_NOFILE` 耗尽触发 `EMFILE`，另有状态回归验证未接管记录清理及重复断开的幂等性。两条回归均已验证修复前失败、修复后通过，转发模块 23 项测试及 Windows GNU 全目标检查通过；Unix 资源故障测试不被计作 Windows 原生故障执行。

### Winsock 布尔选项的实际返回长度

精确提交 `bf69f6c` 的原生 Windows CI `39762239928` 中，四个真实 socket 取消回归均在初始化时报 `invalid forwarding socket close marker size`，不是已通过的 Linux 结果。实现误将 `SO_KEEPALIVE` 查询长度固定为 4 字节。[Microsoft getsockopt 契约](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-getsockopt)要求按返回的实际 `optlen` 解释缓冲区；[socket2 的 Windows Bool 实现](https://github.com/rust-lang/socket2/blob/239dd83a4ced08e514d2c38942aab99791119f0d/src/sys/windows.rs#L112-L143)明确记录该选项的实际提供程序可以返回 1 字节 `BOOLEAN`，或 4 字节 `DWORD`。

现在设置操作继续传 4 字节，查询仍提供零初始化的 4 字节容量，但只接受实际返回长度 1 或 4，并按对应字节解码；0、2、3、负数及超过容量的长度均拒绝，错误包含实际长度。跨平台解码回归覆盖单字节缓冲区之外的非零数据、4 字节非零高位及全部无效长度，四个真实 socket 回归保持启用。Linux 转发模块 24 项测试通过；修复后的原生 Windows 结果必须由新提交 CI 验证，不能用静态检查替代。

## fork 后立即 exec 的 Host 重新入组

统一 Linux 源码样例增加真实 `fork` 后立即 `execv`，避免 Rust `Command` 的 `posix_spawn` 路径绕过两次 Host 登记。原实现只在后续心跳发现旧连接 EOF；exec 保留 PID 和进程创建时间，新 Agent 首次订阅时旧 Host 仍在线，订阅立即失败并触发启动失败关闭。修复前两次原生运行均得到子进程原始状态 9，证据为 `target/diagnostics/native-fork-exec-before.log` 和 `native-fork-exec-before-repeat.log`。

重复登记现在返回明确的 `WouldBlock`。新订阅在同一个 25 秒启动预算内等待旧连接实际退出，每次检查 OS peer 创建时间和会话成员身份；不能替换仍在线的连接。纠正命令的写入及 ACK 等待也使用剩余启动预算，入组后保留原有 35 秒 ACK 超时。直接控制测试确认旧 Host 在线期间不会被替换，旧登记释放后才签发新 Host 的 Enrolled；不回复 ACK 的新 Host 在实际 25.00 秒后超时退出。

exec 同时重建 Runtime，代次计数可能从较大值回到 1。同一个进程身份绑定新 Host 时，协调器先查询并校验事务 ID 和完整 manifest，再使用新代次确认健康；候选事务尚未安装时执行 Prepare/Commit 补齐。选择候选后事务已回滚或完成的晚到 image，必须完成原事务的回滚或 finalize，才能放行。历史终态不会无条件重开；普通重连仍保留旧 Lease 的排空检查。

两条定向状态机回归在修复前实际失败：四次既有切代后 exec 被误回滚；终态后新 image 的 held reservation 被提前放行。修复后覆盖 admit/tick 两种先后顺序、有无预装候选、回滚/finalize 竞态和已完成稳定部署的补齐。证据为 `target/diagnostics/exec-generation-before.log`、`exec-generation-after.log` 及最终完整 Core 日志。真实 fork/exec 的升级前、候选提交后、回滚后三阶段检查已注册既有 Linux Host Suite；最终完整二进制结果以冻结版本的统一 Suite 为准。

## 业务退出码与 Engine 崩溃证据

ptrace 候选策略拒绝 `Command` 启动后，父进程收到 EACCES，系统启动桩明确以 127 退出。原实现将任何非零退出码记为 Engine 故障，健康检查因此错误回滚整组；真实反例保留于 `target/diagnostics/native-ptrace-denied-launch-health-before.log`。同样的误判也会影响明确返回非零业务结果的普通程序，不能为 127 单独添加例外。

Unix 只有明确的 `exit(0..255)` 且没有终止信号时才正常退休，CLI 继续返回目标的真实退出码；信号和未知退出仍是失败。Windows 的退出字段同时包含应用码和异常状态，非负应用码正常处理，所有高位为 1 的状态保守保留为失败，包括断点及访问冲突。Windows 的保守分类依据 [GetExitCodeProcess 返回值](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess) 和 [NTSTATUS 的警告、错误范围](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/using-ntstatus-values)；应用也可以主动返回这些值，因此不将高位分类声称为无歧义的崩溃检测。已有失败证据不会被随后正常退出的报告覆盖。Core 与 CLI 子树汇总使用一致规则，回归覆盖 1、4、42、127、139、255、信号、未知状态及 Windows 异常值。

## exec 保留连接及子进程出生登记

exec 可以保留未设置 CLOEXEC 的业务 TCP。旧连接仍属于原 session/PID，Agent 若将连接编号重新设为 1，新连接会与 resident 中的旧 claim 冲突。真实反例中旧 fd 在 exec 前后均能 echo，新 connect 被严格的唯一性检查拒绝；统一 native 源码回归也在旧完整 CLI 上触发相同的 claim 重用断言，证据为 `target/diagnostics/native-exec-claims-before-source.log`。

Agent 在 Hook 安装前直接使用 fallible OS `SysRng` 选取具有 63 位随机性的非零编号起点，不注册 ThreadRng TLS，也不在 Hook 调用路径生成随机数。每个 image 从该起点单调分配；未初始化的 0 及加法溢出均拒绝，不能重复使用最大编号。ptrace 由常驻 tracer 连续分配，同样在溢出时拒绝。随机起点降低跨 image 冲突概率，不是持久化的无碰撞保证；resident 仍严格拒绝实际冲突，未放松 claim 校验。fork 复制的旧 Socket Lease 继续可用，新 image 不重新认证已建立的旧连接。

ptrace 现在在恢复新 TGID 前同步登记其真实出生信息，fork、vfork 和产生新进程的 clone 均覆盖；同一 TGID 的线程不重复登记。此前只退出或直接崩溃的子进程可能尚未触发网络/审计登记，其真实 SIGSEGV 报告因此被拒绝，活着的 tracer 无法及时向全组确认失败。修复前的源码回归超时且记录 `birth not registered`，证据为 `target/diagnostics/native-ptrace-signal-birth-before-native-fault.log`。

冻结的 r2 CLI 完整执行三项 native Host 场景全部通过，证据为 `target/diagnostics/native-final-release-013-r2-specific-host.log`。每项均验证 fork 后立即 exec、exec 保留旧 TCP 后创建新连接、普通 23/127/139/255 退出不误回滚、真实 native SIGSEGV 仍触发补偿，以及补偿后的原 PID/创建时间、旧 TCP 和文件/进程策略；孤儿 ptrace 场景还实际断言文件与进程拒绝审计。Windows OS 随机源及公共溢出逻辑由跨目标检查覆盖，原生 Windows 运行结果仍以最终 CI 为准。

## Windows 子进程管道的异步 IO 取消

原生 CI 的 worker 回归暴露两个真实失败：无读取子进程的 Bootstrap 写入约 36 秒后才返回，超过 30 秒预算；已有业务连接时关闭控制通道则一直等待。父端通过 `Command` 的 `Stdio::piped` 创建管道，不能以同步 `CreatePipe` 测试替代其真实行为。[Rust 子进程管道实现](https://github.com/rust-lang/rust/blob/1.98.1/library/std/src/sys/process/windows/child_pipe.rs) 使用支持 OVERLAPPED 的父端句柄，并以 `ReadFileEx`、`WriteFileEx` 和完成回调提供同步外观。只调用线程级 `CancelSynchronousIo` 不能取消这些异步请求，导致关闭逻辑等待尚未结束的 IO。

关闭时同时取消实际管道句柄上的异步 IO 和线程上的同步 IO，并等待在途操作真正返回后再释放句柄与缓冲区；[CancelIoEx 契约](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex)明确取消请求不等于 IO 已完成。回归必须使用真实 `Command::piped` 子进程，分别覆盖阻塞读和阻塞写；原 30 秒启动预算及现有连接保留、跨会话撤销、正常半关闭断言保持不变。关键异步阶段增加有界等待以定位失败，Windows Suite 增加 30 分钟步骤上限，避免故障无限阻塞发布。修复后的完整本地工作区、转发模块 24 项测试、真实 Linux 断开场景和 Windows GNU Core 全目标检查通过；新的 Windows 异步管道回归仍需由修复提交的原生 CI 实际执行，不能以交叉编译替代。 后续提交 `4b179d2` 的 CI `39782877773`、Windows job `119838362041` 已实际通过真实子进程 stdio 取消单元、全部 12 项 worker 场景、持久恢复和联合安装；原 30 秒预算及控制通道断开断言均保留。
