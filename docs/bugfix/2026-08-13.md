## 客户端代理隧道死亡时静默直连掩盖真实原因

- 原因：`proxy_https_via_http_proxy` 的 TLS 建连在代理隧道被确认死亡（UnexpectedEof/ConnectionReset/ConnectionAborted/BrokenPipe 或 `tls handshake eof`/`close_notify`）时，会静默用 `connect_direct` 直连 CONNECT 目标重建同一 TLS 载荷。当客户端代理（如 Clash 127.0.0.1:7897）关闭、且内网目标（如 10.2.16.21）只能经代理可达时，直连兜底也失败，git/curl 与 agent 侧只看到 EOF/连接重置等误导性错误（`getaddrinfo() thread failed to start`、`early eof`），掩盖了"客户端代理不可达"这一真实原因。
- 修复：删除 `connect_outbound_through_client_proxy` 内的 `is_dead_tunnel_error` 与 `connect_direct` 直连兜底分支；客户端代理 CONNECT 隧道在 2xx 之后于 TLS 阶段死亡时干净失败，保留真实原因 `tls_mitm_via_client_proxy: upstream TLS handshake failed while validating the real target certificate: tls handshake eof`，由上层（agent/客户端）感知。传输路径由客户端代理决定，serve 不再替客户端静默更换路径。外层 CONNECT 仍如实转发并保留，serve 对原对端说的协议始终是 TLS。
- 验证：将端到端测试替换为 `client_proxy_dead_tunnel_fails_without_direct_fallback`（假代理读 CONNECT 后回 200 随即关闭连接，断言 serve 干净报错且直连目标监听器未收到任何连接）；`hyperhub-core` 105 个测试全部通过。
- 说明：本记录取代 2026-08-11 中"客户端代理 CONNECT 隧道 2xx 后死亡导致上游 TLS 握手 EOF"一节对死隧道直连重试的表述。
