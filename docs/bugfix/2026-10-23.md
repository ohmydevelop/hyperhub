## Windows Hook 清理期间保持应用错误码

诊断提交 `09cf4b4` 的原生 CI `39780021457` 中，联合发布目标正常输出 READY，首次 `TcpStream::connect_timeout` 已在审计中建立本地连接，却返回错误码 0（`The operation completed successfully`），目标随后以 101 退出。此前的原生 Host 升级用例使用阻塞连接，未检出这一返回错误；安装阶段尚未开始。新增诊断保留目标输出、错误和清理前状态，证据为 `target/diagnostics/ci-39780021457-windows.log` 与其统一 Suite artifact。

Host 在业务 API 恢复错误码后仍会访问 FLS 槽、释放 Engine Lease 或卸载模块。内部调用未保证应用线程错误码透明，且 HookGuard 的字段原来在 Drop 函数结束后自动释放。现在使用不可跨线程移动的错误码保护，覆盖 FLS 读写/创建/释放、Engine 清理及 Hook 进入/退出；退出时先在递归保护内释放实际 Engine，再恢复业务调用留下的错误码。该修复保持真实当前 Fiber 槽与原有 Lease 生命周期。[WSAGetLastError 契约](https://learn.microsoft.com/en-us/windows/win32/api/winsock/nf-winsock-wsagetlasterror)说明应用读取的是调用线程的错误状态；本记录不把 FLS API 的内部行为误称为其官方文档保证。

统一 Windows 源码 Probe 新增非阻塞连接 echo、无效 socket 的 recv/ioctl、缺失文件和可执行文件，以及受管理文件拒绝的错误码断言；原联合发布目标继续使用 connect_timeout。新增槽与 Hook 清理单元测试分别检查 Win32 与 Winsock 错误。已有 32 个取消目标进程、4,480 次请求和每组 66 次 FLS 回调要求均保留，连同新模式共 36 个独立目标进程、71 次受管理连接。Linux 联合发布入口同时执行 ptrace 与 Gum，保持 PID、旧连接、共同观察、安装确认和排空断言。修复前两条 Windows 失败日志保留，不通过更换阻塞连接或重试掩盖失败。

本地 Linux Gum 33 项、Windows GNU Agent 全目标检查及格式/脚本检查通过。新错误语义及完整联合发布结果必须由修复提交的原生 Windows CI 实际验证，交叉编译不替代此项。
