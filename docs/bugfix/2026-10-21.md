## 新模块 ABI 的异步租约和错误输出约束

- Host 服务收到发起调用的原始代际租约，而不是在回调到达时重新获取当前代。旧调用可能在新代已生效后才启动异步工作，此时必须克隆原租约，保留正确模块到完成或取消。Native Engine 同时拒绝用其他实例的租约发起调用。
- Host C 回调在拒绝参数前将有效 `written` 输出设为零；防止错误路径保留调用方的旧长度。Rust Host 的 `Err(0)` 也不再被错误解释为成功。
- 回归：真实动态库测试在切换后从旧调用进入 Host 服务并保留后续完成租约，断言新旧两代实际输出不同且归属正确；错误输出单元测试在修复前实际失败，修复后通过。样例沿用统一 runtime Suite；输出初始化属于内部 ABI 校验，直接使用单元测试。
- 当前 runtime 尚未接入现有 CLI、Gum、ptrace 和 Serve。这些修正完善新基础库的边界，不表示已有运行进程的升级流程已改变。

## 网络 Engine 调用上下文的线程退出保护

继续接入同步 Hook 的原代租约时，Linux 显式 Gum 在 `/bin/true` 启动边界稳定出现 TLS `AccessError`，随后因 C 回调不能展开而 abort。原因是原生线程清理还会执行已 Hook 的 IO，但租约 TLS 已先销毁。

现在先初始化 ArcSwap 的线程数据，再初始化调用上下文；通过无析构标记与 `try_with` 识别已销毁的 TLS，线程清理时不再访问它。普通状态锁错误仍进入原有校验路径，不因此跳过策略。补充晚析构访问单元测试，以及 `linux_thread_exit_probe.c`：线程退出析构关闭文件，父线程验证文件完整内容，已注册到 ptrace/显式 Gum 统一 Suite。启动边界与完整 Suite 均恢复通过；Suite 同时保留嵌入式 Gum 启动 stderr 以便定位后续失败。

本条属于尚未发布的网络 Engine 接入，Windows 代码通过 GNU 编译检查，原生行为由当前提交 CI 验证。完整自动升级协调、其他 Hook 组和跨协议连续性仍在计划中。

## Windows 模块缓存并发发布的共享冲突

网络接入提交 `867b955` 的 [CI 39628172821](https://github.com/ohmydevelop/hyperhub/actions/runs/39628172821) 中，Linux 两个任务通过，Windows 新 Host/Engine 回归通过，但八线程缓存安装回归实际出现 `os error 32`。已有目标被校验器以禁止写入/删除共享的句柄持有时，Windows 的不覆盖发布可能先返回共享冲突，而不是文件已存在；同时原实现发布时仍持有写句柄。

修正为先同步、设为只读并关闭写句柄，再发布。Windows 发布失败而目标已存在时，继续验证目标的文件类型、权限、大小和摘要，不替换已映射对象。新增持有目标校验句柄的 Windows 定向回归，保留原八线程回归，并先等待全部安装线程结束再做断言，防止失败清理与尚在写入的线程竞争。

完整 workspace、runtime/Engine 严格 Clippy、格式和 Windows GNU 全目标检查在本机通过；Windows 定向执行由本修正提交的原生 CI 验证。该问题属于内部缓存状态及文件共享语义，使用直接单元/集成测试，不新增目标程序 Benchmark。
