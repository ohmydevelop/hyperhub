## Git 443 明文/客户端代理流量被误判为 TLS MITM

- 原因：命中连接级 `protocol = "git"` 规则且目标端口为 443 时，`serve` 无条件对客户端执行 TLS MITM 握手。但 Git Smart HTTP 可运行在明文 `http://host:443/...` 上，经本地 HTTP 代理（如 Clash）时客户端首包又是 `CONNECT`；两者都不是 TLS ClientHello，rustls 以 `InvalidContentType` 终止握手。HTTPS 分支已有的 `proxy_https_via_http_proxy` 与明文判断在 Git 分支缺失。
- 影响：`git clone/fetch/push` 使用 `http://` 加 443 端口或经由本地代理访问 Git 主机时，连接报 `git_https_mitm: client TLS MITM handshake failed; target rejected or aborted the HyperHub certificate: received corrupt message of type InvalidContentType`，Git 操作失败。
- 修复：Git 分支 443 端口按首包探测结果选择传输方式：明文 Smart HTTP（含 HTTP 方法）走 `proxy_http`；HTTP `CONNECT` 走 `proxy_https_via_http_proxy` 完成代理握手后再对隧道做 TLS MITM；只有真正收到 TLS 首包或尚无可判定数据时才走 `proxy_https`。
- 验证：新增 `git_https_transport` 三路选择单元测试（明文 Smart HTTP、客户端代理 CONNECT、TLS ClientHello），`hyperhub-core` 全部 70 个测试保持通过。

## HTTP CONNECT 隧道内重复转发 CONNECT 导致上游 TLS 握手 EOF

- 原因：客户端（git/libcurl）通过 HTTP 代理发 `CONNECT host:443` 时，`proxy_https_via_http_proxy` 把客户端的 CONNECT 报文**原样再写进上游连接**。但上游连接在 `connect_for` 阶段已建立完毕：直连目标时它就是到 TLS 服务器的 TCP 连接，经配置的 HTTP/SOCKS5 代理时 `http_connect_handshake` 也已建好隧道。重复写入 CONNECT 会把 HTTP 文本塞给 TLS 服务器（或污染已建隧道），目标直接断开。
- 影响：`git clone https://git.example.com/...` 等经 HTTP 代理（或命中 `no_proxy` 后直连）的场景报 `tls_mitm_via_client_proxy: upstream TLS handshake failed while validating the real target certificate: tls handshake eof`，Git 操作失败。内网目标因常命中 `no_proxy` 而直连，更易触发。
- 修复：`proxy_https_via_http_proxy` 只消费并校验客户端的 CONNECT，然后向客户端回 `HTTP/1.1 200 Connection Established`，随即直接对已建立的 `proxy` 连接执行 TLS MITM（`proxy_https`），不再读取或转发任何上游代理响应。
- 验证：新增端到端测试 `client_connect_is_acknowledged_without_corrupting_upstream`，验证 CONNECT 收到 200、隧道内 TLS 握手成功且应用数据（ping/pong）贯通；`hyperhub-core` 78 个、`hyperhub` 23 个测试全部通过。

## 客户端 HTTP 代理隧道指向代理自身导致上游 TLS 握手 EOF

- 原因：客户端（git/libcurl）配置了 HTTP 代理时，注入代理拦截到的是通往该代理地址（如 Clash 127.0.0.1:7897）的连接，serve 的 `connect_for` 按该地址建连，随后才从首包识别出 `CONNECT host:443` 并把目标改写为真实主机。此时已建立的 `proxy` 流只是到客户端代理的裸 TCP 连接，serve 未向其转发 CONNECT 就发送 TLS ClientHello，代理端直接断开。
- 影响：`hyperhub run git clone https://git.example.com/...` 在客户端 HTTP 代理路径下报 `tls_mitm_via_client_proxy: upstream TLS handshake failed while validating the real target certificate: tls handshake eof`（Windows 上为 os error 10053 ConnectionAborted），Git 操作失败。
- 修复：`proxy_https_via_http_proxy` 完成客户端 MITM 握手后，若上游 TLS 握手因隧道断开（UnexpectedEof/ConnectionReset/ConnectionAborted/BrokenPipe）失败且 CONNECT 目标是内网地址（RFC1918/回环/链路本地/唯一本地，含 hostname 回退），则用 `connect_direct` 直连真实目标重试并继续 MITM，审计记录 `upstream_fallback/direct_fallback`；`connect_outbound_tls` 改为保留底层错误类型以便判定。
- 验证：新增 `dead_proxy_tunnel_falls_back_to_direct_for_private_target` 端到端测试，死隧道 + 内网目标回退直连后 ping/pong 贯通；`hyperhub-core` 79 个、`hyperhub` 23 个测试全部通过。

## 客户端 HTTP 代理 CONNECT 端到端保留（状态机根因修复）

 - 原因：上一轮修复采用伪造 `HTTP/1.1 200 Connection Established` + 启发式直连兜底处理客户端 HTTP 代理 CONNECT：既丢失上游代理的响应语义（如 407 鉴权失败），又用 `is_private_target`/`is_dead_tunnel_error` 做不透明的失败回退。这属于头痛医头：没有把"客户端代理协议必须端到端保留"建模为状态机不变量，导致代理响应不可见、失败路径不可解释。
 - 修复：从第一性原理把"serve 对原对端说的协议 = 客户端对原对端说的协议"定为不变量，外层代理协议（HTTP CONNECT/SOCKS5/absolute-form）端到端保留，MITM 只替换被审计的最内层。`proxy_https_via_http_proxy` 恢复为：读客户端 CONNECT 头 → 原样写上游代理（保留 `Proxy-Authorization` 等）→ 读代理响应原样中继给客户端 → 2xx 后 `accept_client_tls` + `connect_outbound_tls` + `serve_https_tunnel`，非 2xx 干净结束。删除 `git_https_transport`、`connect_outbound_with_direct_fallback`、`is_private_target`、`is_dead_tunnel_error` 与伪造 200 分支；Git 443 明文/HTTPS 分支并入同一 `classify_ingress` + `plan_for` 分派表（`PlainHttp` 覆盖 `http://host:443` 明文 Smart HTTP）。
 - 影响：经 HTTP 代理的 Git/HTTPS 连接（含代理返回 407 需鉴权、公网目标等场景）不再依赖伪造响应与死隧道兜底，代理的响应语义原样可见；`connect_for` 如实记录 `UpstreamTransport`（Direct/Tunneled）供审计与分派。
 - 验证：删除过时测试 `client_connect_is_acknowledged_without_corrupting_upstream` 与 `dead_proxy_tunnel_falls_back_to_direct_for_private_target`；新增 `client_connect_is_forwarded_to_the_http_proxy_before_tls_mitm`（CONNECT 原样到达假代理、200 中继、TLS MITM 后 ping/pong 贯通）与 `http_proxy_authentication_failure_is_relayed_to_the_client`（407 原样中继、不发起 MITM）；`hyperhub-core` 83 个、`hyperhub` 23 个测试全部通过。
 - 说明：本文档此前的三条记录（Git 443 明文/客户端代理流量被误判、隧道内重复转发 CONNECT、隧道指向代理自身导致 EOF）描述的是被本状态机修复取代的旧修复路径，最终以本记录为准。

## 客户端代理 CONNECT 隧道 2xx 后死亡导致上游 TLS 握手 EOF

 - 原因：客户端（git/libcurl）经本地 HTTP 代理（如 Clash 127.0.0.1:7897）访问内网 Git 时，serve 按状态机把客户端 CONNECT 原样转发给代理、代理 2xx 响应原样中继（外层代理协议端到端保留）。但代理返回 200 并不保证隧道可用：内网目标（如 10.2.16.21）常不在代理可路由范围内，代理 200 后隧道随即死亡，serve 在隧道内做上游 TLS 校验时读到 EOF，报 `tls_mitm_via_client_proxy: upstream TLS handshake failed while validating the real target certificate: tls handshake eof`，git clone/fetch/push 失败。该场景与 serve 是否配置 CA 无关（CA 只影响客户端侧 MITM 证书，失败在上游侧）。
 - 修复：`proxy_https_via_http_proxy` 的 TLS 建连改为 `connect_outbound_through_client_proxy`：先在代理隧道内做上游 TLS 握手；若隧道被确认死亡（UnexpectedEof/ConnectionReset/ConnectionAborted/BrokenPipe 或 `tls handshake eof`/`close_notify`），则用 `connect_direct` 直连 CONNECT 目标重建同一 TLS 载荷并继续 MITM，审计事件 `upstream_fallback/direct_fallback` 记录原始代理错误。对端与协议不变（serve 对原对端说的仍是 TLS），外层 CONNECT 已如实转发并保留；与旧启发式不同，不再按目标是否内网分类，任何目标只要代理隧道确认死亡都走直连重试。
 - 影响：内网 Git/HTTPS 经本地 HTTP 代理的场景恢复可用；代理隧道真实死亡时不再以 EOF 告警，而是直连目标完成审计，直连也失败时返回带上下文的直连错误。本记录是对上一节"不再依赖死隧道兜底"表述的修正：保留的并非伪造 200 或按内网分类的启发式，而是代理隧道确认死亡后的同一 TLS 直连重试。
 - 验证：新增端到端测试 `client_proxy_dead_tunnel_falls_back_to_direct_tls_mitm`（假代理读 CONNECT 后回 200 随即关闭连接，断言 serve 直连 CONNECT 目标后 TLS MITM 且 ping/pong 贯通）；`hyperhub-core` 84 个、`hyperhub` 23 个测试全部通过。
