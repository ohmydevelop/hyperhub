# Linux `run bash` 与原始 Bash 启动行为不一致（已修复）

## 现象

在远程 Linux 主机上执行：

```text
(base) ubuntu@a:~$ hyperhub run bash
HyperHub password:

bash-5.2$ bash
(base) ubuntu@a:~$
```

`hyperhub run bash` 进入后显示默认的 `bash-5.2$`，再次执行一个普通 `bash` 后才显示带 Conda 环境的 `(base) ubuntu@a:~$`。这与直接启动原始 Bash 的提示符和环境初始化行为不一致。

## 初步判断

- `hyperhub run bash` 通过内部 PTY 启动器和注入流程启动目标 Bash，目标可能不是以登录 Shell 方式启动。
- 首层 Bash 的 `HOME`、`TERM`、`PS1`、`SHELL`、`BASH_ENV` 或启动文件加载条件可能与直接启动 Bash 不同，因此没有加载用户的 `.bashrc`/Conda 初始化。
- 再次执行的子 Bash 继承了终端和环境，并重新加载用户启动文件，所以显示 `(base)` 提示符。

## 待验证

- 对比原始 Bash 与 `hyperhub run bash` 中的 `argv`、`$0`、`$-`、`$HOME`、`$TERM`、`$PS1` 和 `shopt login_shell`。
- 确认 PTY 启动器是否需要保持目标命令的 Shell 模式，且不应擅自改变用户的启动文件语义。
- 验证 `hyperhub run bash -l`、`hyperhub run bash -i` 与直接执行 `bash -l`、`bash -i` 的行为差异。

## 影响

交互式 Bash 的提示符、Conda 初始化、别名、函数及用户启动脚本可能未按直接启动 Bash 的方式生效，容易让用户误判当前运行环境和 HyperHub 注入状态。

## Linux Bash 修复记录（2026-08-31）

PTY launcher 现在显式保留用户原始命令的 `argv[0]`、参数、工作目录和继承环境，不自动追加 `-l` 或 `-i`，因此裸 `hyperhub run bash`、`hyperhub run bash -l` 和 `hyperhub run bash -i` 分别保持 Bash 自身的启动语义。已增加 launcher 参数保真测试；真实 Linux 交互式 Bash、Conda 和启动文件行为仍应在 Linux 发布环境完成验收。
