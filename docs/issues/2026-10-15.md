## TODO：Linux ptrace 遗漏 sendmmsg DNS 关联，导致外部 Fake-IP 被拒绝

- 用户反馈：通过 `hyperhub run` 执行调用 System One 的 curl 脚本失败；尚缺完整启动命令及终端报错，不能将某一日志会话与用户请求唯一对应。
- 排查证据：本机系统解析器将 `api.typesafe.ai` 解析为 `198.18.3.131`；网关多次在 curl 会话认证成功后记录 `PermissionDenied: unknown or expired session Fake-IP`。
- 当前实现：`crates/hyperhub-core/src/socks.rs` 在 SOCKS 请求没有域名、且地址无法通过当前会话的 Fake-IP 映射还原时，将整个 `198.18.0.0/15` 地址段判定为未知或过期的会话 Fake-IP 并拒绝。外部 DNS 使用相同地址段时可能触发此路径。
- 已确认根因：本机 curl 默认通过 glibc 同时查询 A/AAAA，使用 `sendmmsg` 发送 DNS 报文。`crates/hyperhub-cli/src/platform/linux/syscall_supervisor.rs` 的 `dns_enter` 仅处理 `sendto`、`sendmsg`、`write`；未记录查询时，后续 `recvfrom` 也不会进入 DNS 响应关联，`dns_addresses` 缺少域名映射，最终 SOCKS 请求只能携带 IP。
- 对照复现：最小 C 程序查询本地 DNS，查询名固定为 `localhost`，响应固定为 `198.18.99.7`，再连接本地 echo 服务。通过当前 PATH 中的 HyperHub 执行时，`sendto`、`sendmsg`、`write` 三种发送方式均成功，网关审计显示目的域名 `localhost` 和地址 `127.0.0.1`；仅改成 `sendmmsg` 就稳定返回 SOCKS reply 4、`Permission denied`，网关记录同一 Fake-IP 错误。DNS 服务和 echo 服务均位于本机回环地址。
- curl 路径验证：对实际安装的 curl 跟踪发现，默认解析使用 `sendmmsg`，`--ipv4` 解析改为 `sendto`。跟踪时通过本地诊断库阻止所有非回环 `connect`，未建立真实 API 连接；不能据此声称 `--ipv4` 已完成真实 API 请求。
- 影响：当 DNS 返回外部 Fake-IP 且域名映射丢失时触发显式拒绝；真实 IP 场景也可能丢失域名，影响依赖目的域名的处理，具体影响需按协议继续验证。
- 修复方向：补齐批量 DNS I/O 关联，正确处理每条报文和实际成功数量，并检查 `recvmmsg` 接收路径。保留未知或过期会话 Fake-IP 的拒绝语义，不能通过直接放行整个地址段规避域名丢失。
- 后续回归：将本地 DNS 和最小目标程序源码整理为统一 Suite 回归，覆盖批量与非批量 DNS I/O、A/AAAA、域名传递及未知会话 Fake-IP 拒绝语义。当前仅完成诊断，临时源码、跟踪和结果保存在 `target/diagnostics/fake-ip/`；未修改实现、未执行真实 API 请求，也未验证 Windows、macOS 或其他 Linux 架构。

### 已通过本地对照确认

1. **TODO：TCP Fast Open 绕过网关入口，优先修复。** `syscall_supervisor.rs:665` 只在普通 `connect` 上重定向 TCP。`sendto`、`sendmsg` 携带 `MSG_FASTOPEN` 可以隐式建立 TCP 连接，未进入此路径。本地 echo 对照中，普通 connect 的内核 peer 是 SOCKS 端口，而两种 Fast Open 的内核 peer 都是原目标端口；三个 HyperHub 会话仅普通 connect 产生网关 connect/close 审计。已验证直接连接，路由 deny、凭证和其他策略的独立组合尚未执行。修复需覆盖隐式建连及首包发送顺序；无法保持语义的路径应明确拒绝。API 语义参见 [Linux send(2)](https://man7.org/linux/man-pages/man2/send.2.html)。

2. **TODO：DNS vectored/batch I/O 关联不完整。** 除此前确认的 `sendmmsg`，`dns_enter` 也不处理 `writev`、`readv` 和 `recvmmsg`。本地 DNS 固定返回 `198.18.99.7`，sendto/recvfrom、sendto/recvmsg 对照均成功，仅替换为 writev/recvfrom、sendto/readv、sendto/recvmmsg 就出现同一 Fake-IP 拒绝。manifest 已列出 file.readv/file.writev，但文件入口命中不代表 DNS 语义被覆盖。修复需逐报文处理，并覆盖实际成功数量、分散缓冲区、错误和部分成功。

3. **TODO：同一 UDP socket 上多个 DNS 查询发生域名错配。** `syscall_supervisor.rs:169` 的查询表仅以 `(pid, fd)` 保存一个域名；发送新查询覆盖旧值，`:790` 收到响应时使用当前值，不匹配响应 transaction ID、question 和 resolver。复现先发送 `localhost` 再发送 `ip6-localhost`，收到第一个查询返回的 `198.18.99.7` 后连接，网关实际将其作为 `ip6-localhost` 解析并连接到 `::1`，对照路径应为 `localhost`/`127.0.0.1`。echo 字节仍正确，只有核对域名和真实目的地址才能发现。修复需按 DNS 事务与响应 question 关联；同 IP 多域名和过期映射还需进一步设计，不能只用全局 IP→最后域名证明正确。

4. **TODO：共享 fd 表与按进程复制的状态模型不一致。** `syscall_supervisor.rs:298`、`:468` 对不同线程组复制 descriptor 状态，未区分 `CLONE_FILES` 共享表。最小程序先创建非阻塞 TCP socket，再 `clone(CLONE_FILES | SIGCHLD)`；子进程关闭并把同一 fd 复用为阻塞 UDP socket。父进程 `SO_TYPE` 确认为 UDP，native `F_GETFL` 报告 blocking，HyperHub 却报告 nonblocking。修复应区分 fd 表身份、fd generation 和 open file description，连同共享表 close/dup、unshare、exec 分裂覆盖。`close_range(CLOEXEC)` 已有专门处理，本轮未将其误列为缺失。

### 静态确认的实现缺口，影响尚需目标平台或策略实验

5. **TODO：Windows GetAddrInfoExW 丢弃异步完成与取消参数。** `windows_gum/adapters/network.rs:402` 将调用者的 OVERLAPPED、completion routine 和 name handle 参数忽略，转发时传入 null/None；回退及 reentrant 路径也如此。调用结果和同步耗时可能改变，调用者提供的事件、回调或取消句柄不能按原调用方式工作。同步成功路径不能证明异步兼容。需 Windows 源码样例覆盖立即完成、pending、事件、回调和取消。参见 [Microsoft GetAddrInfoExW](https://learn.microsoft.com/en-us/windows/win32/api/ws2tcpip/nf-ws2tcpip-getaddrinfoexw)。A 入口也丢弃参数，但 Win32 文档对 A/W 异步支持存在区别，优先以 W 入口建立回归。

6. **TODO：Windows ConnectEx 的初始数据可能先于 SOCKS 握手发送。** `windows_gum/adapters/network.rs:818` 将目标替换为 SOCKS 地址后，仍把原 `send_buffer/send_length` 传给 ConnectEx。`capabilities/gateway/network_redirect.rs` 只对 Blocking connect 请求立即握手，Extended connect 的握手延后到 socket I/O。若 ConnectEx 自带非空首包，该首包可能直接成为 SOCKS 监听器收到的应用数据。需 Windows 本地服务验证非空首包、空首包、异步完成及应用直接等待响应的路径。参见 [Microsoft ConnectEx](https://learn.microsoft.com/en-us/windows/win32/api/mswsock/nc-mswsock-lpfn_connectex)。本轮仅静态确认参数与握手顺序，未声称 Windows 运行结果已验证。

7. **TODO：Linux 文件映射缺少 Read 意图检查。** ptrace `file_intent` 的 mmap/mprotect 分支（`:1089`）以及 Gum `adapters/native.rs:1372`、`:1117` 只检查 PROT_WRITE。O_RDWR 打开被归为 Write 后，读取 syscall 仍可单独检查 Read，但只读 mmap 或 PROT_READ 升级没有相应 Read 检查。已持有 fd 或配置 read deny/write allow 时存在读取策略缺口风险。需隔离配置下验证 read 与 write 分离、预先打开 fd、热更新、MAP_PRIVATE/MAP_SHARED 和权限升级；当前未执行带拒绝策略的实验，未将其报告为已实测绕过。

### 测试覆盖模型问题与待明确边界
