# Codex 全量 ptrace 保底基线（2026-09-18）

## 目标

本轮只验证最坏条件下的通用正确性，不启用 seccomp-BPF 或 Codex 专用优化：

- `codex-cli 0.154.0`；
- x86_64 static PIE，约 251 MiB；
- 已 stripped，无 `PT_INTERP`、无动态依赖和可用符号；
- 不提供 Agent runtime，不初始化 Frida/Gum；
- 静态 syscall supervisor 对所有 syscall 执行 `PTRACE_SYSCALL` entry/exit 跟踪。

真实对话命令：

```sh
codex exec \
  --ephemeral \
  --skip-git-repo-check \
  --ignore-rules \
  --json \
  'Reply with exactly: HYPERHUB_CODEX_OK'
```

HyperHub 组只增加通用 `hyperhub run`，产品代码没有 Codex 名称、路径、版本或特征码分支。

## 正确性结果

Native 与 HyperHub 样本均：

- exit code 为 0；
- 包含 `thread.started`、`turn.started`、`item.completed` 和 `turn.completed`；
- 最终消息精确为 `HYPERHUB_CODEX_OK`；
- JSONL 输出完整；
- 可选 MCP 服务错误在两组中均存在，不属于 HyperHub 回归。

一次开启通用 Hook report 的对话记录到 29,069 次 manifest 点位命中，覆盖大量 read/write、mmap、descriptor、socket、DNS、clone、exec 和 wait syscall；对话仍正常完成。这证明该结果确实经过全量 ptrace supervisor，而不是绕过静态后端。

## 配对性能基线

交替执行 3 组 native/全量 ptrace 真实对话：

| 模式 | 样本 | 中位数 |
| --- | --- | ---: |
| Native | 8.442 s、6.449 s、7.940 s | 7.940 s |
| HyperHub 全量 ptrace | 9.285 s、8.133 s、8.877 s | 8.877 s |

当前配对样本中，全量 ptrace 增加 0.937 秒，为 native 的 1.12 倍。短命令仍有约 200–250 ms 的固定 Session、supervisor 和生命周期成本。

此前出现过约 138 秒的非配对 HyperHub 样本，但恢复纯全量 ptrace 后无法复现，因此不能把该异常直接归因于 ptrace，也不能把其消失作为 seccomp 优化收益。后续性能结论必须使用同一版本、同一配置、交替执行的配对样本。

## 阶段结论

第一阶段以全量 ptrace 的正确性作为唯一基线，不通过减少 Hook 点、识别 Codex 或依赖可选内核能力换取速度。第二阶段先优化全量 ptrace 路径本身；seccomp-BPF 等能力只能在第三阶段作为可关闭、可回退、与本基线语义等价的加速路径。
